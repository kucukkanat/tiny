An extension is the only kind of feature there is. Every screen the app has is
one, and so is anything you add yourself.

Two ways to deliver it, and the difference is **when**. One listed in
`packages/app/src/extensions.tsx` ships in the bundle, and adding it is a commit
and a deploy — chat, settings and the extensions screen are all this. One that
isn't listed is `import()`ed in the tab when somebody installs it, live in the
next message, with no build and nothing on a server.

Same type, same registry, same screen, same switch. `@tiny/extension-manager`
holds the registry; `@tiny/extension-starter` is a real one, served next to the
app, that the app does not list.

:::note
This is the **only** way to give the model a tool. There used to be a
`plugin-tools` that let you write one in a textarea; it was a second mechanism
for the same job, so it is gone.
:::

## What one looks like

The default export is a function of the host that returns a plain object. There
is no `activate`, nothing to tear down, and no side effects — which is what makes
turning one off exactly as cheap as turning it on.

```tsx
import type { Extension, Tiny } from '@tiny/host'
import { tool } from 'ai'
import { z } from 'zod'

export default (tiny: Tiny): Extension => ({
  id: 'dice',
  title: 'Dice',
  tools: {
    roll: tool({
      description: 'Roll an n-sided die.',
      inputSchema: z.object({ sides: z.number() }),
      execute: ({ sides }) => 1 + Math.floor(Math.random() * sides),
    }),
  },
})
```

## Every slot

`id` and `title` are required. Everything past them is optional:

| Slot             | What it adds                                                       |
| ---------------- | ------------------------------------------------------------------ |
| `Screen`         | a route at `/#/<id>`, rendered by the shell                        |
| `Sidebar`        | a section in the left sidebar                                      |
| `tools`          | functions the model can call mid-answer                            |
| `providers`      | a model API, offered in Settings beside Anthropic and OpenAI       |
| `actions`        | an entry in the bar shown when a passage of a reply is highlighted |
| `messageActions` | a button in the footer of a message, beside Copy                   |
| `instructions`   | a line added to the model's system prompt                          |
| `css`            | a stylesheet, adopted while the extension is on                    |

`Screen` is optional — a tools-only extension has no screen, and a
sidebar-only one has no page worth showing.

[Every slot](/extensions/slots) takes each one in turn, with a module you can
paste into the editor and run.

## What the host hands you

The platform you didn't bring, and the fold of what every extension did.
Everything else is already there: `localStorage` for your own state,
`react-router` to navigate, Tailwind on the app's tokens to look right.

```ts
type Tiny = {
  readonly useChats: () => readonly Chat[]
  readonly useModel: () => LanguageModel | undefined
  readonly ask: (question: string, options?: readonly string[]) => Promise<string>
  readonly useTools: () => ToolSet
  readonly useInstructions: () => string | undefined
  readonly useActions: () => readonly ChatAction[]
  readonly useMessageActions: () => readonly MessageAction[]
  readonly useProviders: () => Registry
}
```

`useChats()` is every conversation, newest first, read-only. `useModel()` is the
configured model, or `undefined` while there is not one. `ask()` puts a question
in the chat and waits for the answer — which is how a tool can ask the person at
the keyboard something only they know. The five reads below them are the fold:
what every live extension registered, yours included.

:::note
`Tiny` only ever grows. A module already sitting in someone's `localStorage` is
bound to the shape it was written against, and there is no migration that reaches
it — so `useModel` returns a `LanguageModel` and always will.
:::

## What you may import

This is the whole of what being in the build buys you. A bundled extension is in
the app's module graph, so it can reach `@tiny/ui`, an `@ai-sdk/*` provider,
anything in the workspace.

One that arrives at runtime gets five bare specifiers, resolved by an import map
in the page, and no relative imports at all — a blob has no base to resolve
against:

```
react   react/jsx-runtime   react-router   zod   ai
```

Only those, and only because a second copy of each genuinely breaks: React and
the router carry context, and one zod is what keeps a `.describe()` in what the
model is told. Everything else you bundle yourself, so the cost lands on whoever
installs it rather than on every first visit.
